# EventFlow — регистрация на мероприятия

Кейс №9 из набора заданий Agentic Developer. Сервис регистрации на мероприятия:
организатор создаёт событие с лимитом мест, участники регистрируются по email,
при заполнении включается лист ожидания, на входе билеты отмечаются чекином.

## Чем делали

Claude Code (CLI-агент Anthropic) с моделью Claude Sonnet 5
(`claude-sonnet-5`) — проверено по служебным данным текущей сессии (и в
контексте, и полем `model` в самом файле лога сессии), не угадано. Выбор
инструмента: агентный CLI с прямым доступом к shell/файловой системе/браузеру
позволяет не просто сгенерировать код, а сразу проверить его — поднять
Postgres, дважды выстрелить конкурентными запросами, открыть два окна
браузера — и держать честный журнал решений с реальными временными метками
рядом с кодом, а не отдельно от него.

## Состояние проекта

Реализовано:

- организатор: логин, создание/редактирование события (лимит мест нельзя
  опустить ниже уже занятых, перенос даты запрещён в прошлое);
- участник: публичная страница события, регистрация по email, лист ожидания;
- страница участника по `access_token`: статус, код билета, отказ от участия
  с автоматическим продвижением первого из очереди (продвижение не происходит,
  если событие уже началось — очередь просто перестаёт двигаться, отмена
  места по-прежнему разрешена);
- регистрация после начала события запрещена (`409 event_already_started`),
  как и её перенос в прошлое (см. этап 2);
- организаторский просмотр эмулированных писем (замена реальной почты);
- чекин на входе по коду билета (атомарно, повтор кода не удваивает счётчик)
  и экран организатора со счётчиками зарегистрировано/в очереди/пришло,
  обновляющимися live по WebSocket (авторизация — той же сессионной cookie);
- фоновый воркер: напоминание за 24ч до события (один раз на версию
  расписания), уведомление о переносе даты всем активным участникам, эмуляция
  «отправки» всех pending-писем с проверкой актуальности перед отправкой.

Не реализовано: реальная доставка писем на настоящий email (эмуляция —
запись в БД со статусом `sent`/`skipped`, видимая организатору в «Письмах»).
Это не пробел, а сознательный выбор в рамках допустимого заданием: «Внешние
сервисы можно эмулировать. Почту, сторонние API и подобное можно заменить
заглушками» — прямое требование общих условий, не наше послабление.

## Как эмулируется почта — и как это проверить

Участник не видит билет или ссылку на свою регистрацию сразу в ответе на
регистрацию: ответ всегда одинаковый, независимо от результата (это осознанное
решение — email не доказывает владение регистрацией, подробности идут только
«в письме»). Реальная отправка не подключена, поэтому «письмо» — это запись в
таблице `notifications`, а увидеть её текст (со ссылкой на страницу участника)
может только организатор.

Чтобы пройти сценарий целиком:

1. Зайти в приложение организатора (`http://localhost:5173`), войти с данными
   из `backend/.env` (`ORGANIZER_EMAIL`/`ORGANIZER_PASSWORD`).
2. Создать событие или открыть существующее, нажать **«Публичная страница»** —
   откроется `/e/<id>` в новой вкладке. Эту ссылку в реальности рассылали бы
   участникам.
3. На публичной странице зарегистрироваться по email. В ответ — нейтральное
   сообщение вида «Если регистрация возможна, письмо придёт на указанный
   email» — это ожидаемо, не ошибка.
4. Вернуться в приложение организатора, открыть **«Письма»** у того же
   события — там видна строка с этим email, типом письма (`Билет` или
   `В лист ожидания`) и рабочей ссылкой **«открыть»**.
5. Перейти по ссылке — откроется `/my/<access_token>`, страница участника: там
   статус (подтверждено / в очереди / отменено), код билета (если место есть)
   и кнопка «Отказаться от участия».

Тот же путь через `curl` (без браузера) — предполагается, что backend уже
поднят и есть cookie организатора после `/api/auth/login`:

```bash
# 1. регистрация участника (ответ всегда нейтральный)
curl -X POST http://localhost:3000/api/events/<event-id>/registrations \
  -H "Content-Type: application/json" -d '{"email":"participant@example.com"}'

# 2. организатор смотрит "письма" события и берёт ссылку из payload
curl -b cookies.txt http://localhost:3000/api/events/<event-id>/notifications

# 3. открыть ссылку из ответа (my_registration_url) или обратиться напрямую
curl http://localhost:3000/api/my/<access_token>
```

## Фоновый воркер (напоминания, перенос, эмуляция отправки)

Запускается автоматически внутри backend-процесса каждые 30 секунд
(`WORKER_INTERVAL_MS` в `.env`), плюс один раз сразу при старте. Делает два
дела за один проход:

1. Создаёт `reminder`-уведомление для каждого подтверждённого или уже
   отмеченного на входе (`checked_in`) участника, до события которого
   осталось ≤24ч и оно ещё не началось — ровно одно на текущую версию
   расписания (`schedule_version`), не зависит от того, сколько раз воркер
   запускался или сколько раз перезапускался backend (гарантия — уникальный
   индекс в БД, а не память процесса).
2. Забирает все `pending`-уведомления по одному и эмулирует отправку, заново
   проверяя актуальность именно перед отправкой, а не полагаясь на то, что
   было верно в момент постановки в очередь:
   - регистрация отменена → `skipped: registration_cancelled`, для любого
     типа письма;
   - `waitlist`-письмо, а участник уже продвинут из очереди (стал confirmed
     или checked_in) → `skipped: promoted_since_queued` — про очередь
     напоминать нечего, у него уже есть отдельное `ticket`-письмо;
   - `reminder`/`reschedule` относится к уже неактуальной версии расписания
     (событие перенесли ещё раз) → `skipped: stale_schedule_version` — эти
     типы письма сообщают конкретную дату, и старая версия просто устарела;
   - `reminder`, событие которого уже наступило → `skipped:
     event_already_started`.

   **`ticket`/`waitlist` не пропускаются из-за версии расписания.** Они
   сообщают не дату, а факт «у вас есть место»/«вы в очереди» — этот факт не
   устаревает от переноса даты. Если событие перенесли раньше, чем воркер
   успел обработать такое письмо, оно всё равно уходит (`sent`), но с
   актуальными на момент отправки датой и названием события — они
   подставляются заново из `events`, а не берутся из снимка на момент
   регистрации.

Ручной запуск одного тика (полезно для проверки и для тестовых сценариев,
где нужен предсказуемый момент обработки, а не следующий по таймеру):

```bash
cd backend && npm run worker
```

Два одновременных `npm run worker` не обрабатывают одну и ту же запись дважды
— `SELECT ... FOR UPDATE SKIP LOCKED` на уровне PostgreSQL.

**Что означает «однократность» здесь.** Гарантируется одна запись в БД на
`(регистрация, тип письма, версия расписания)` и одна попытка её обработки.
Реальной отправки на почту нет — это не заявка на exactly-once доставку
настоящим email-провайдером (у которых её в принципе никто не гарантирует),
а честная эмуляция: единственный проверяемый факт — что в БД ровно одна
запись и она обработана ровно один раз.

## Интеграционный сценарий

Воспроизводимые сценарии на отдельных тестовых событиях (не тестовый
фреймворк — обычный скрипт): гонка за последнее место (двое одновременно),
третий участник вторым в очереди (иначе FIFO не доказать — одному элементу
порядок ни к чему), повторная регистрация тем же email не меняет число
активных строк, отмена продвигает **первого по `seq`** с билетом и оставляет
**второго** в очереди без билета, повторный чекин одним кодом отклоняется,
повторный тик воркера не создаёт дублей. Отдельно, на своих тестовых
событиях (общее событие выше к этому моменту уже содержит отменённые/
продвинутые/отмеченные чекином регистрации и не показательно): напоминание
за 24ч создаётся и отправляется ровно один раз на участника, повторный тик
не дублирует; перенос даты пропускает уже ждущее отправки устаревшее по
`schedule_version` напоминание (`skipped: stale_schedule_version`, а не
отправка со старой датой) и создаёт собственное `reschedule`-уведомление,
которое доходит, не лишая участника места. Проверяет через API и напрямую
через БД, не только по HTTP-кодам (у публичных ответов кейса намеренно
нейтральные статусы). Не печатает `access_token`/`ticket_code`, удаляет
только свои тестовые события по их `id`, ничего больше в базе не трогает
явно.

**Важная оговорка про воркер.** `runWorkerTick()`/`createDueReminders()` —
**глобальные функции по всей подключённой БД**, не только по тестовым
событиям сценария. Если БД общая с реальной работой через приложение,
сценарий заодно обработает и её pending-уведомления (безопасно — то же
самое сделал бы и сам backend в течение ближайших `WORKER_INTERVAL_MS`, но
раньше срока). Поэтому ни одна проверка не доверяет агрегатным числам,
которые возвращают эти функции (`remindersCreated`/`notificationsProcessed`)
— только состоянию `notifications`, отдельно отфильтрованному по
`event_id`/`registration_id` именно этого прогона; чужие данные в БД не
могут исказить результат проверки.

**Перенос даты (проверка 8) гонится с фоновым интервалом backend.** Эта
проверка намеренно оставляет одно напоминание pending между его созданием и
переносом даты. Если в этот момент успеет сработать собственный фоновый тик
backend (`WORKER_INTERVAL_MS`, по умолчанию 30с), он обработает напоминание
раньше переноса — и проверка «устаревшее напоминание пропускается» ничего
не докажет (сценарий упадёт с понятным сообщением, а не пройдёт ложно).
Перед прогоном сценария стоит поднимать backend с большим
`WORKER_INTERVAL_MS`, например `3600000` (час) — ниже это учтено в обеих
командах запуска; сценарий также печатает предупреждение в консоль, если
интервал маленький.

**Backend и сценарий обязаны смотреть в один и тот же `DATABASE_URL`.**
Сценарий сам подключается к БД (`pool` из `db.ts`) и одновременно дёргает
запущенный backend по HTTP — если у них будет разный `DATABASE_URL`, сценарий
создаёт данные через API в одной базе, а проверяет и чистит за собой —
в другой. Итог не «сценарий упадёт с понятной ошибкой», а тестовое событие
останется висеть в базе backend, а сценарий ещё и завершится с непонятной
на первый взгляд ошибкой вида «ожидались 2 регистрации, найдено 0» — это
воспроизведено и проверено отдельно, не гипотеза.

Чтобы полностью изолировать проверку от реальных данных, нужно поднять
**отдельную тестовую БД и запустить оба процесса — backend и сценарий —
с одним и тем же `DATABASE_URL`, указывающим на неё**:

```bash
# Отдельная база в том же Postgres (может быть и совсем другой сервер)
docker exec eventflow-db-1 psql -U eventflow -d eventflow -c \
  "create database eventflow_test owner eventflow;"

export DATABASE_URL="postgres://eventflow:eventflow@localhost:5433/eventflow_test"
export WORKER_INTERVAL_MS=3600000   # не дать фоновому тику обогнать сценарий
npm run migrate
npm run seed
npm run dev        # тот же DATABASE_URL/WORKER_INTERVAL_MS уже в окружении

# в другом терминале, с тем же DATABASE_URL:
export DATABASE_URL="postgres://eventflow:eventflow@localhost:5433/eventflow_test"
npm run scenario
```

Предварительное условие для обычного (не изолированного) запуска — backend
уже поднят (`npm run dev`) на БД с применёнными миграциями и сидом
организатора, и сценарий запускается из того же окружения (`backend/.env`),
то есть с тем же `DATABASE_URL`, что и сам backend. Если backend уже
запущен с маленьким `WORKER_INTERVAL_MS` (по умолчанию) — перезапусти его с
`WORKER_INTERVAL_MS=3600000` перед сценарием, иначе проверка переноса даты
может изредка ложно упасть (см. оговорку выше):

```bash
cd backend && npm run scenario
```

Завершается кодом `0` при успехе и `1` при любой проваленной проверке.

## Стек и почему

- **Backend: Node.js + TypeScript + Express.** Один язык на весь стек упрощает
  работу с агентом и ревью; Express достаточно для небольшого API без лишних
  абстракций.
- **PostgreSQL.** Нужны транзакции и блокировки строк (`SELECT ... FOR UPDATE`) —
  ими решается гонка за последнее место на событии.
- **Frontend: React + Vite** (шаблон `create-vite react-ts`).
- Оба сервиса — на предпочтительных вариантах из общих требований задания.

## Предварительные требования

- Node.js 20+ (проверено на v24.11.1) и npm
- Docker Desktop (или любой Docker с поддержкой `docker compose`)
- Порт 5433 на хосте свободен для PostgreSQL (5432 намеренно не используется,
  чтобы не конфликтовать с другими локальными базами), порты 3000 и 5173 — для
  backend и frontend

## Что сделали бы следующим заходом

- **Расширить автоматические интеграционные проверки** (`npm run scenario`
  уже покрывает гонку за последнее место, FIFO очереди, дубликат email,
  двойной чекин, отсутствие дублей у воркера при повторном тике, напоминание
  за 24ч ровно один раз и перенос даты с пропуском устаревшего напоминания
  и доставкой reschedule-уведомления) — остаются непокрытыми: отмена
  регистрации или перенос события ровно во время обработки уведомления
  воркером (проверено только вручную, см. `docs/decisions.md`), и
  одновременный запуск двух воркеров над одной очередью — оба завязаны на
  реальный тайминг двух параллельных процессов, что труднее воспроизвести
  детерминированно в одном скрипте, чем через `pg_sleep()` в ручной `psql`-
  сессии, поэтому пока проверено только так. Также прогонять
  `npm run scenario` в CI на отдельной тестовой БД, а не только вручную
  локально — workflow для этого настроен (`.github/workflows/scenario.yml`:
  отдельный Postgres-сервис на каждый прогон, `migrate`+`seed`+`dev`+
  `npm run scenario`), и вся последовательность команд проверена локально на
  изолированной одноразовой БД, но **сам workflow ещё не подтверждён зелёным
  прогоном на GitHub Actions** — это станет известно только после push и
  первого реального запуска.
- **Live-обновление публичных страниц участника** — `/e/:id` (остаток мест)
  и `/my/:token` сейчас читаются один раз при загрузке; WS-канал есть только
  у организаторского экрана чекина. Причина выбора объёма: именно там WS
  нужен для требования «работает при двух одновременно открытых клиентах» в
  его самом конкурентном виде (два экрана чекина с живым счётчиком), а
  участник обычно держит страницу открытой недолго и один раз; корректность
  остатка мест при этом гарантирует не отображение на странице, а блокировка
  строки события на сервере в момент самой регистрации.
- **Ограничение времени чекина** — `POST /api/checkin` сейчас не проверяет,
  что событие уже началось; отметить билет технически можно и заранее. В
  ожидаемом поведении кейса №9 это не требуется явно («билет проходит
  чекин один раз» — про повтор кода, не про время), поэтому оставлено за
  рамками обязательного объёма, а не упущено по невнимательности.
- **Роли организаторов** — сейчас один общий аккаунт из `.env`, без
  разделения по событиям и без восстановления пароля. Общие требования
  прямо оставляют модель входа на усмотрение реализации («Учётные записи и
  вход — на ваше усмотрение... можно обойтись без входа»); один аккаунт —
  минимальный достаточный объём для кейса с одним организатором.
- **Более устойчивое переподключение WS** — сейчас фиксированная задержка
  1.5с без экспоненциального backoff и без предела попыток; для локальной
  демонстрации достаточно, для продакшена — нет.
- Очистка старых `sent`/`skipped` записей в `notifications` — таблица растёт
  без ограничения; для локального объёма одного кейса это не создаёт
  проблем на практике, и ни общие требования, ни кейс №9 не описывают
  удержание истории писем, поэтому ретеншн не добавлялся — не забытая
  часть обязательного объёма, а не поднятый вопрос.

**Текущее ограничение, а не задел на будущее:** реальная доставка email не
подключена — «письмо» это запись в `notifications` со статусом
`sent`/`skipped`, видимая организатору в «Письмах» (см. раздел про
эмуляцию почты выше). Проверки того, что система ведёт себя правильно, в
подавляющем большинстве ручные — curl, прямые SQL-запросы и живые сессии в
браузере, а не автоматизированный набор тестов.
