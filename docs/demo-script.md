# Демо-скрипт EventFlow (5-7 минут)

Рабочий текст для выступления. Реплики описывают только проверенное
репетицией 2026-10-02 (см. `docs/decisions.md`). Конкретные коды билетов и
`id` события здесь не фиксируются — при реальном прогоне событие
создаётся заново и получает новые значения.

## 0. Вступление (0:00-0:30)

«EventFlow — сервис регистрации на мероприятия. Организатор создаёт
событие с лимитом мест, участники регистрируются по публичной ссылке,
система сама ведёт лист ожидания и чекин на входе.»

## 1. Гонка за последнее место и FIFO (0:30-2:00)

Событие с лимитом 2. Сначала — обычная регистрация Анны: место занято,
статус «Место подтверждено».

Затем — два параллельных запроса на последнее оставшееся место: от
Бориса и от Карлы одновременно. Оба получают с виду одинаковый ответ
API — специально нейтральный: он не раскрывает результат конкретной
регистрации (подтверждена или в очереди) и не выдаёт, существует ли уже
запись по этому email.

«Кто именно получил место — по этому ответу не видно. Покажу
по-другому.» → открываю «Письма»: видно, что для Бориса создано
уведомление с билетом, для Карлы — уведомление о листе ожидания (статус
может быть «Ожидает обработки» или уже «Отправлено (эмуляция)» —
фоновый воркер в dev тикает раз в 30 секунд, при необходимости можно
обновить экран или подождать). Следом регистрирую Дмитрия — ему тоже
создано уведомление о листе ожидания, вторым.

Открываю страницу участника Дмитрия: «В листе ожидания», «позиция 2».
Очередь упорядочена по `seq`, который присваивается при записи
регистрации в транзакции с блокировкой строки события — то есть по
порядку, в котором заявки реально были зафиксированы на сервере, а не
по тому, чей ответ быстрее дошёл до браузера.

## 2. Отмена и продвижение очереди (2:00-2:45)

Анна отказывается от участия на своей странице → статус «Регистрация
отменена», код билета — зачёркнут, бейдж «аннулирован».

Открываю страницу Карлы: она автоматически продвинулась — «Место
подтверждено», новый код билета. Это FIFO: первой продвигается та, кто
раньше встала в очередь, а не Дмитрий, вставший позже. Проверяю
страницу Дмитрия — он остался в очереди, но позиция обновилась на 1.

## 3. Чекин и WebSocket (2:45-3:45)

Открываю экран «Чекин» в двух вкладках браузера — например, как если бы
на входе стояли два волонтёра. Ввожу код билета Бориса в одной вкладке
→ счётчик «Пришло» обновляется сразу в обеих, без обновления страницы —
это WebSocket, а не опрос сервера.

Ввожу тот же код ещё раз → «Этот билет уже отмечен на входе», счётчик
не увеличивается второй раз. Один билет нельзя отметить дважды.

## 4. Перенос даты и повторная почта (3:45-4:30)

Меняю дату события в редактировании. Открываю «Письма» — появились три
новые записи «Перенос события»: Борису, Карле и Дмитрию, то есть всем,
кто сейчас реально участвует. У Анны, отказавшейся раньше, такой записи
нет — уведомление не рассылается тем, кто уже вышел из события.

## 5. Ограничения (4:30-5:15)

«Что сейчас не сделано: писем в реальный почтовый ящик — нет, таблица
«Письма» эмулирует то, что отправил бы фоновый воркер. Это сознательное
решение для тестового задания, не случайный пробел. Ещё два ограничения:
аккаунт организатора один, без ролей и нескольких учётных записей; и
страницы участника `/my/:token` не обновляются вживую — в отличие от
экрана «Чекин» с WebSocket, здесь после продвижения очереди или чекина
нужно обновить страницу вручную, чтобы увидеть новый статус.»

## 6. Роль агента в работе (5:15-6:15)

«Я задал основные правила и разбил работу на проверяемые этапы. Когда
проверки выявили, что перенос даты лишает участника исходного письма, а
воркер читает состояние без нужных блокировок, я потребовал исправить
эти нарушения и перепроверить конкурентные сценарии».
