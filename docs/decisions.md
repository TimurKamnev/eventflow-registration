# Журнал решений

Формат: дата и время в Asia/Bishkek (реальные, по ходу работы), что сделано,
почему так, а не иначе. Запись делается в процессе или сразу после этапа, не
задним числом.

## 2026-09-29, 14:50–15:25 (Asia/Bishkek) — Этап 1: каркас

Начало сессии зафиксировано инструментом (лог сессии Claude Code,
`2026-09-29T08:50:15Z` UTC = `14:50` Asia/Bishkek).

Решения:

- **Backend: Node.js + TypeScript + Express.** Один язык на весь стек, минимум
  зависимостей для API такого размера.
- **PostgreSQL, отдельный контейнер через docker-compose.** Порт хоста — 5433,
  а не стандартный 5432: на машине уже работает Postgres другого проекта
  (`messenger_db`) на 5432, конфликтовать с ним нельзя.
- **Frontend: React + Vite**, сгенерирован официальным шаблоном
  `create-vite react-ts`, стартовая страница заменена на минимальную проверку
  связи с backend (fetch `/health/db`).
- **CORS.** Backend и frontend — разные origin (порты 3000 и 5173), браузер
  блокирует такие запросы без заголовков CORS. Добавлен пакет `cors` с открытой
  политикой для локальной разработки (`origin: *`). Для продакшена это нужно
  сузить, но проект локальный — отмечаю как осознанное упрощение.
- **Время: UTC в базе и в бэкенде, отображение — фиксированный Asia/Bishkek.**
  Без выбора часового пояса пользователем (в отличие от кейса 1 Notetaker, где
  это требование) — для регистрации на мероприятия это не требуется явно,
  упрощение сознательное.

Уточнения архитектуры (приняты до начала кода, будут реализованы на следующих
этапах):

- Уведомления: таблица `notifications` с уникальным ключом
  `(registration_id, type, schedule_version)`, вставка `ON CONFLICT DO NOTHING`
  в той же транзакции, что меняет состояние. Гарантия — «ровно одна запись-
  намерение», не exactly-once доставка через SMTP (доставка эмулируется).
- `schedule_version` на событии, инкремент при переносе даты — открывает новое
  окно для одного нового напоминания на участника без потери истории старых.
- Повторная регистрация после отказа: частичный уникальный индекс
  `(event_id, lower(email)) WHERE status <> 'cancelled'` — отменённая запись
  остаётся как история, новая регистрация создаёт новую строку и заново
  проходит логику лимита/листа ожидания.

Проверка этапа:

- `docker compose up -d db` → контейнер `eventflow-db-1` в состоянии `healthy`.
- `curl http://localhost:3000/health` → `{"status":"ok"}`.
- `curl http://localhost:3000/health/db` → `{"status":"ok","now":"<UTC>"}` —
  подтверждает реальное подключение к PostgreSQL, а не заглушку.
- Открыл `http://localhost:5173` в браузере (Chrome, через инструмент
  автоматизации) — страница показывает статус backend и время БД, то есть
  кросс-origin fetch с 5173 на 3000 реально проходит (CORS настроен верно).
- После проверки оба dev-сервера остановлены (`kill` по портам 3000 и 5173).

Не сделано на этом этапе (осознанно, по плану): схема БД для событий и
регистраций, любая бизнес-логика, UI регистрации/билета — по плану это следующий
этап (30 сентября).

## 2026-09-30, 08:14–08:21 (Asia/Bishkek) — Этап 2: миграции, авторизация, CRUD события

Перед стартом уточнили дизайн (обсуждение, не код): `access_token` (секрет для
своей регистрации) отделён от `ticket_code` (для чекина); уведомление о месте в
листе ожидания — отдельный тип `waitlist` с access_token, билет по продвижению —
отдельным письмом типа `ticket`; повторный `POST` на активный email должен
отвечать нейтрально, без статуса и секретов; занятые места = `confirmed +
checked_in`; `seq` для FIFO присваивается внутри транзакции с блокировкой
события; воркер отправки перепроверяет актуальность перед отправкой (отдельно
от поллера, который только создаёт записи); нельзя уменьшить `capacity` ниже
уже занятых мест.

Решения этапа:

- **Схема без фреймворка миграций.** Один идемпотентный файл
  `backend/db/schema.sql` (`create table if not exists` + `create index if not
  exists`), применяется скриптом `npm run migrate`. На размере проекта
  отдельный migrations-фреймворк (knex/node-pg-migrate) — лишняя зависимость;
  если схема начнёт часто меняться версионно, это станет ограничением —
  фиксирую как известный компромисс.
- **`notifications.type`** уже включает `waitlist` (создаётся при постановке в
  очередь) наравне с `ticket`/`reminder`/`reschedule`, хотя сама рассылка
  появится позже — так схема не потребует правки, когда дойдём до Registration
  API.
- **Auth — одна учётная запись организатора.** Таблица `organizers`, сид из
  `.env` (`ORGANIZER_EMAIL`/`ORGANIZER_PASSWORD`, `bcryptjs`), сессия — JWT в
  httpOnly-cookie (`jsonwebtoken`, `SESSION_SECRET` из `.env`, срок 12ч).
  `requireOrganizer` защищает все `/api/events*`. Без ролей, без восстановления
  пароля — минимум, достаточный для локального теста.
- **CORS сужен.** Было `cors()` с `origin: '*'` (этап 1); теперь куки на
  каждый запрос нужны для авторизации, а `credentials: true` несовместимо с
  `origin: '*'` — заменил на явный `FRONTEND_ORIGIN` (`http://localhost:5173`
  по умолчанию).
- **Правило порядка PATCH:** `schedule_version` растёт только при изменении
  `starts_at`; проверка `capacity < occupied` — только при изменении
  `capacity`; обе проверки и апдейт — в одной транзакции с
  `SELECT ... FOR UPDATE` на строку события.

Проверка этапа (полный список ниже, в ответе пользователю) — миграция и сид на
пересозданной с нуля БД, вход/отказ в доступе без cookie, создание события с
датой в прошлом отклонено, смена только `capacity` не трогает
`schedule_version`, смена `starts_at` увеличивает версию на 1, ограничение
`capacity < occupied` проверено на тестовых данных, вставленных напрямую в
`registrations` (Registration API в этом этапе не существует), два
одновременно открытых окна браузера после независимого логина видят один и тот
же список событий, редактирование в UI корректно показывает время в
Asia/Bishkek.

Не сделано (по плану, следующий этап): регистрация участника, лист ожидания,
чекин, реальная рассылка уведомлений, WebSocket.

## 2026-09-30, 08:37–08:43 (Asia/Bishkek) — точечные исправления этапа 2 перед коммитом

По итогам независимого ревью внесены правки, до коммита:

- **Единая валидация для POST и PATCH.** Вынесена в `backend/src/validation.ts`
  (`parseTitle`/`parseDescription`/`parseStartsAt`/`parseCapacity`,
  `ValidationError`). Раньше `updateEvent` был мягче создания: принимал пустой
  `title`, нестроковый `description` и, главное, **перенос события в прошлое**
  (проверка «дата в будущем» была только в `createEvent`). Теперь оба
  обработчика используют одни и те же функции.
- **Внутренние ошибки БД не возвращаются клиенту.** `handleError` в
  `events.ts`: `ValidationError` → `400` с текстом ошибки (безопасен, это наш
  же текст), любая другая ошибка → `500 {"error":"internal_error"}`, реальная
  причина только в `console.error` на сервере.
- **Найден и исправлен более серьёзный баг при проверке предыдущего пункта:**
  при обрыве соединения с БД процесс backend падал целиком (необработанное
  событие `'error'` на `pg.Pool` — см. https://node-postgres.com/apis/pool#error).
  Без этого воспроизвести «клиент не видит внутренний текст ошибки» было
  невозможно: ошибка не долетала до клиента вообще, потому что процесс был
  уже мёртв. Добавлен `pool.on('error', ...)` в `db.ts`. Это не было
  запрошено отдельно, но напрямую блокировало проверку — исправлено в рамках
  того же точечного изменения.
- **Воспроизводимый SQL-сценарий для capacity** сохранён в
  `backend/db/fixtures/capacity_scenario.sql`. При первой версии сценарий тихо
  вставлял только 1 из 3 строк: `ticket_code` уникален глобально, а литералы
  `'TICKET-A'`/`'TICKET-B'` уже были заняты более ранними ручными тестовыми
  данными в той же локальной БД — `ON CONFLICT DO NOTHING` (без указания цели)
  тихо съел именно эти вставки. Заметил по тому, что проверка
  `capacity=1 → 400` неожиданно прошла как `200`. Исправлено: коды генерируются
  случайно (`'TICKET-' || upper(encode(gen_random_bytes(4), 'hex'))`), email
  сделаны специфичными для фикстуры (`capacity-fixture-*@example.com`), чтобы
  не пересекаться с данными из будущих ручных тестов.
- **Проверил `FRONTEND_ORIGIN` в `index.ts` побайтово** (`od -c`) — обычная
  строка `"http://localhost:5173"`, без markdown-разметки.

Все проверки (auth, валидация POST/PATCH построчно, перенос в прошлое,
`schedule_version`, ограничение `capacity`, устойчивость к падению БД)
повторены с нуля на пересозданной БД — результаты в ответе пользователю.
Не закоммичено.

## 2026-09-30, 08:44–08:49 (Asia/Bishkek) — ужесточение validation.ts перед коммитом

Второй раунд правок по итогам ревью, только `validation.ts`:

- **`parseCapacity`** раньше приводил через `Number(value)`, из-за чего
  строка `"3"`, `null` (→ `0`, отклонялось по `<= 0`, но случайно, не по типу)
  и `boolean` (`true` → `1`, реально прошло бы как `capacity=1`!) вели себя
  непредсказуемо. Теперь строгая проверка `typeof value !== "number"` —
  строки, `null`, `boolean` и дробные отклоняются на уровне типа, а не
  приведения.
- **`parseStartsAt`** раньше принимал любую строку, которую понимает
  `new Date(...)`, включая `"2026-11-01T10:00:00"` без зоны — такая строка
  парсится JS как локальное время процесса, то есть один и тот же запрос
  давал бы разный момент в UTC в зависимости от `TZ` окружения, где запущен
  backend (в контейнере — обычно UTC, на чьей-то машине — нет). Добавлена
  проверка регулярным выражением на обязательный `Z` или `±HH:MM` перед
  парсингом.

Проверено (POST и PATCH, полная матрица) — результаты в ответе пользователю:
`capacity` как строка/`null`/`boolean`/дробное/отрицательное/ноль отклонены,
целое положительное число проходит; `starts_at` без зоны отклонён и на POST,
и на PATCH, `Z` и `+06:00` — приняты и дают одинаковый момент в UTC, мусорная
строка и число вместо строки отклонены.

Закоммичено (см. `git log`), запушено в `origin/main`.

## 2026-09-30, 08:54–09:03 (Asia/Bishkek) — Этап 3: регистрация, лист ожидания, страница участника

Реализовано строго в рамках запрошенного объёма: публичная страница события,
регистрация по email, лист ожидания, страница участника по `access_token`,
отказ с автопродвижением, организаторский просмотр эмулированных писем.
Чекин, реальная рассылка, напоминания и WebSocket сознательно не начаты.

Решения:

- **`access_token` выдаётся всегда, `ticket_code` — только при confirmed.**
  `access_token` — `crypto.randomBytes(32)` в base64url (секрет для ссылки из
  письма), `ticket_code` — 8 символов из алфавита без похожих букв/цифр
  (0/O, 1/I/L), для чекина вручную. Оба генерируются в `backend/src/ids.ts`.
  Коллизии не перехватываются retry-циклом — при uuid-подобной энтропии
  вероятность пренебрежимо мала для масштаба одного мероприятия; если это
  станет проблемой, добавить `ON CONFLICT` retry.
- **Один тип уведомления `ticket`** и на немедленное подтверждение, и на
  продвижение из листа ожидания — это одно и то же событие в жизненном цикле
  регистрации («вот ваш билет»), происходит ровно один раз, конфликтов по
  уникальному ключу `(registration_id, type, schedule_version)` не бывает.
- **Нейтральный ответ `POST /api/events/:id/registrations`** — везде и всегда
  одинаковый `202 {message: "..."}`, независимо от того, новая это
  регистрация, повтор, confirmed или waitlisted. Внутренняя логика (лист
  ожидания, дубликат email) не протекает в ответ.
- **Единая точка блокировки — строка события.** Регистрация, отмена и
  продвижение из очереди берут `SELECT ... FOR UPDATE` на `events` в одном и
  том же порядке (событие → нужная(ые) строка(и) `registrations`), поэтому
  все операции, меняющие занятость мест или порядок очереди, сериализуются
  через один и тот же лок — как и `PATCH` события из этапа 2.
- **Защита в глубину при вставке.** Помимо блокировки события, у
  `(event_id, lower(email))` остаётся частичный уникальный индекс из этапа 2;
  если он всё же сработает (unique_violation, код `23505`), обработчик ловит
  это и отвечает тем же нейтральным сообщением, а не 500.
- **`checked_in` нельзя отменить** — проверка в `cancelMyRegistration`, хотя
  эндпоинта чекина ещё нет: правило нужно уже сейчас, так как это часть
  контракта отмены, которую я пишу в этом этапе. Проверено вручную (см. ниже).
- **Просмотр писем — только организатору.** `payload` содержит
  `access_token`-ссылку и `ticket_code`, это фактически чужая почта — эндпоинт
  защищён тем же `requireOrganizer`, что и остальной organizer API.
- **Фронтенд: свой мини-роутер по `window.location.pathname`** (`/e/:id`,
  `/my/:token`), без `react-router` — всего два публичных маршрута, лишняя
  зависимость не оправдана. Важно: все вызовы `useState` в `App` идут первыми,
  безусловно — ранний `return` для публичных маршрутов только в JSX ниже, а не
  до хуков (иначе порядок хуков менялся бы между рендерами — сам поймал у себя
  эту ошибку до проверки, см. ниже).

Проверка этапа (полный список с результатами — в ответе пользователю):
- Два одновременных `POST` на событие с `capacity=1` — ровно один confirmed
  (с `ticket_code`), второй waitlisted, оба уведомления верного типа.
- Отказ подтверждённого участника → продвинут именно первый по `seq` из
  очереди, ему создано новое уведомление `ticket`; второй в очереди остался
  waitlisted.
- Повторная регистрация того же email (в т.ч. с другим регистром букв) —
  второй строки в БД не появилось, ответ идентичен первому.
- Доступ по случайному и по «почти правильному» токену — `404` в обоих
  случаях; по настоящему `access_token` — `200`.
- `checked_in` (выставлен вручную через SQL, эндпоинта ещё нет) → попытка
  отмены даёт `409`, место остаётся занятым.
- Просмотр писем без cookie организатора → `401`; с cookie → список виден.
- Перезапуск backend-процесса (без миграций и сида) → та же регистрация по
  тому же `access_token` отвечает идентично — данные пережили рестарт, потому
  что живут в PostgreSQL, а не в памяти процесса.
- Сквозной прогон в реальном браузере: организатор создаёт событие → участник
  регистрируется на публичной странице (видит нейтральное сообщение) →
  организатор находит письмо в «Письмах» → переходит по ссылке → видит статус
  и код билета → отменяет участие → статус меняется на «отменено».

Не закоммичено. К чекину, напоминаниям и WebSocket не приступал.

## 2026-09-30, 11:55 (Asia/Bishkek) — исправления по ревью транзакций

Два точечных исправления в `registrations.ts` до коммита этапа 3, по итогам
ревью:

- **`registerForEvent` больше не трактует любой `23505` как «email уже
  зарегистрирован».** Раньше единственная проверка была `err.code === "23505"`
  — под это подпадала и коллизия `access_token`/`ticket_code` (просто неудачно
  сгенерированное случайное значение, никак не связанное с email), и её тоже
  тихо превращали в «успешно, ждите письмо». Теперь код смотрит на
  `err.constraint`: `registrations_active_email_idx` — действительно дубликат
  активной регистрации на email (нейтральный ответ, как и раньше);
  `registrations_access_token_key` / `registrations_ticket_code_key` —
  коллизия сгенерированных значений, транзакция откатывается и вся попытка
  регистрации повторяется заново (до 3 раз) с новыми `access_token`/
  `ticket_code` — партия не потеряна молча. Имена constraint'ов проверены
  напрямую в БД (`\d registrations`), совпадают с константами в коде.
- **Регистрация после начала события запрещена** (`409
  {"error":"event_already_started"}`) — проверка на `event.starts_at <= now()`
  сразу после блокировки строки события, до проверки email (это общая политика,
  не зависит от того, зарегистрирован ли email — поэтому обычный явный ответ,
  а не нейтральный).
- **Отмена после начала события не продвигает очередь.** Отмена самого места
  по-прежнему разрешена, но блок поиска и продвижения первого waitlisted
  теперь под условием `!eventAlreadyStarted`.

## 2026-09-30, 12:46–13:00 (Asia/Bishkek) — Этап 4: чекин и live-счётчики (WebSocket)

Реализовано строго в рамках запрошенного: `POST /api/checkin`, экран
организатора со счётчиками confirmed/waitlisted/checked_in, WebSocket-канал
для live-обновления этих счётчиков. Напоминания не начинал.

Решения:

- **`POST /api/checkin`** — один атомарный `UPDATE ... WHERE ticket_code=$1
  AND status='confirmed' RETURNING event_id`. Повторный ввод того же кода не
  находит строку в статусе `confirmed` второй раз — счётчик не задвоится без
  какой-либо отдельной блокировки, гарантия на уровне самого `WHERE`.
  Отдельным `SELECT` (только если `UPDATE` не задел ни одной строки)
  различаю причину для организатора: не найден / уже отмечен / не подтверждён
  (лист ожидания или — важный нюанс — **отменённая регистрация сохраняет свой
  старый `ticket_code` как историю**, поэтому код от неё формально «существует»,
  но не даёт пройти).
- **WebSocket поверх того же HTTP-сервера** (`server.on('upgrade', ...)` +
  `WebSocketServer({noServer:true})`), не отдельный порт — меньше движущихся
  частей для локального запуска.
- **Авторизация WS — та же сессионная cookie**, что и у REST: во время
  HTTP-апгрейда читаю `Cookie` заголовок вручную (пакет `cookie`, экспорт
  называется `parseCookie` в установленной версии 2.x — не `parse`, как в
  доке для v1) и проверяю тот же JWT, что и `requireOrganizer`. Без валидной
  cookie — `401` прямо на апгрейде, до создания сокета.
- **В сообщениях WS — только агрегированные числа** (`{type, eventId,
  confirmed, waitlisted, checked_in}`), никаких `email`/`access_token`/
  `ticket_code`. Обеспечено самой формой payload, а не отдельной фильтрацией —
  протечь нечему.
- **Подписка по `eventId` из query-строки апгрейда**, рассылка — при любой
  мутации, влияющей на счётчики: регистрация (только если реально создана
  новая строка, не для нейтрального ответа на дубликат), отмена/продвижение,
  чекин.
- **Клиент всегда переподписывается REST-ом.** `connect()` в `CheckinView`
  вызывает `api.eventCounts()` и только затем открывает `WebSocket` — и при
  первом монтировании, и в каждой попытке переподключения (`ws.onclose` →
  `setTimeout(connect, 1500)`). Так изменения, случившиеся во время разрыва,
  не зависят от того, дошло ли конкретное WS-сообщение.

Неожиданная находка при проверке переподключения: убийство процесса backend
(`kill` по порту 3000) стабильно вызывало **полную перезагрузку** вкладки
браузера (подтверждено — внедрённая в `window` диагностическая переменная
пропадала). Это не код приложения (нигде нет `location.reload()`) — похоже
на поведение среды автоматизации браузера (Chrome/CDP) при обрыве
соединения с портом, к которому был открыт WS, а не баг продукта. Не стал
тратить время на дальнейшую диагностику этого конкретного механизма —
вместо убийства процесса проверил переподключение внутри страницы
(`ws.close()` из JS), что и является тем событием, которое реально
обрабатывает код (`onclose`), без постороннего влияния среды.

Проверено (полные результаты — в ответе пользователю):
- Верный код → `200`, счётчики обновились.
- Повторный ввод того же кода → `409 already_checked_in`, счётчик не растёт.
- Несуществующий код → `404 not_found`.
- Код отменённой (была confirmed, потом cancelled) регистрации → `409
  not_confirmed` — это и есть практический аналог «кода из очереди»:
  waitlisted в принципе не имеет `ticket_code` (он `null`), а
  единственный код, который «есть, но не работает» — от отменённой брони.
- Чекин без cookie → `401`, апгрейд WS без cookie → `401` на HTTP-уровне (до
  установления сокета), с валидной cookie → `101 Switching Protocols`.
- Два открытых клиента на экране чекина одного события — оба получили
  одинаковое обновление счётчиков одновременно после чекина через третий

- Переподключение (`ws.close()` из JS, без убийства процесса): `close` →

## 2026-09-30, 13:05–13:15 (Asia/Bishkek) — точечные исправления этапа 4 перед коммитом

По итогам ревью — два исправления в `ws.ts`/`CheckinView.tsx`, плюс правка
подписей счётчиков:

- **Проверка `Origin` при апгрейде WS**, наравне с cookie. Браузер сам
  подставляет заголовок `Origin` для запроса, инициированного со страницы, и
  JS со страницы не может его подделать — сверяю с `FRONTEND_ORIGIN` до
  проверки cookie. Отсутствующий или чужой `Origin` → `403`, ещё до чтения
  cookie.
- **`ws.onopen` тоже перезапрашивает counts.** Подписка на сервере
  регистрируется синхронно при обработке апгрейда — раньше, чем клиенту
  приходит успешный handshake, — поэтому в момент `onopen` подписка уже
  железно активна. Раньше был только один REST-запрос в момент `connect()`,
  до создания сокета; событие, случившееся между этим запросом и моментом
  реальной подписки, не попало бы ни в тот GET (мог уйти раньше), ни в
  первый WS-пуш (подписки ещё не было).
- **Побочная находка при проверке предыдущего пункта**, требующая
  исправления, чтобы сам fix не сломался на практике: два `refreshCounts()`
  за одно подключение (в `connect()` и в `onopen`) могут прийти в обратном
  порядке, если первый идёт медленнее второго (нормальная ситуация в
  реальной сети, не гипотетическая). Без защиты более медленный, но более
  старый ответ мог откатить экран назад после того, как второй, более
  свежий, уже всё показал правильно. Добавлен счётчик `latestSeq`: каждый
  `refreshCounts()` запоминает свой номер и применяет `setCounts` только если
  он всё ещё последний; входящее WS-сообщение тоже увеличивает `latestSeq`,
  инвалидируя любой ещё летящий `GET`.
- **«Зарегистрировано» = `confirmed + checked_in`, «Пришло» = `checked_in`.**
  Раньше счётчик «Зарегистрировано» показывал только `confirmed` — после
  чекина человек как будто «переставал быть зарегистрированным», хотя он по
  прежнему занимает место, просто уже пришёл. API/WS payload не менял
  (`confirmed`/`waitlisted`/`checked_in` как были, это удобные «сырые»
  строительные блоки) — сложение сделано на уровне отображения в
  `CheckinView`.

Проверено (полные результаты — в ответе пользователю):
- WS-апгрейд с чужим `Origin` + валидной cookie → `403`, даже без `Origin`
  вовсе → `403`; верный `Origin` без cookie → `401`; оба верны → `101`.
- Разрыв между начальным GET и моментом реальной подписки: воспроизведён
  детерминированно (не полагаясь на удачный тайминг) — патчем `fetch` в
  браузере задержана **доставка** (не отправка) самого первого `/counts`
  ответа на 2.5с, реальный запрос при этом ушёл на сервер немедленно и
  захватил снимок до мутации. Мутация (чекин) сделана через curl сразу после
  открытия экрана. Быстрый `onopen`-запрос успел отразить актуальное

  ответ вообще пришёл; когда тот в итоге пришёл (с устаревшим снимком

## 2026-09-30, 13:40–13:49 (Asia/Bishkek) — Этап 5: фоновая обработка notifications

Реализовано строго в рамках запрошенного: создание напоминаний за 24ч,
reschedule-уведомления при переносе, безопасная построчная обработка pending
(эмуляция отправки) с проверкой актуальности перед «отправкой». Финальный этап
(что бы это ни было — README, итоговая проверка) не начинал.

Решения:

- **Concurrency — `FOR UPDATE SKIP LOCKED`, не отдельный статус
  `processing`.** Один SQL-паттерн для очереди задач в Postgres: воркер берёт
  `SELECT ... WHERE dispatch_status='pending' ORDER BY created_at FOR UPDATE
  SKIP LOCKED LIMIT 1` внутри транзакции — если строка уже заблокирована
  другим воркером, эта просто пропускается и берётся следующая свободная, без
  ожидания и без риска обработать одну и ту же запись дважды. Не потребовалась
  правка enum `dispatch_status` — работает поверх уже существующих
  `pending`/`sent`/`skipped`.
- **Напоминания — один SQL `INSERT ... SELECT ... ON CONFLICT DO NOTHING`**,
  без цикла по регистрациям в приложении: `WHERE r.status='confirmed' AND
  e.starts_at > now() AND e.starts_at <= now() + interval '24 hours'`.
  Уникальность `(registration_id, type, schedule_version)` — та же, что и у
  ticket/waitlist — даёт «один раз на schedule_version» бесплатно, не
  зависящее ни от количества прогонов воркера, ни от рестарта backend
  (гарантия живёт в БД, не в памяти процесса).
- **Reschedule-уведомления** вставляются в `updateEvent` (events.ts) той же
  `INSERT ... SELECT` формой, но **только когда `startsAtChanged`** — правка
  одного `capacity`/`title`/`description` их не создаёт (условие явно
  проверено, см. код). Активные участники — `status in ('confirmed',
  'waitlisted')`; `cancelled` — уже не участвует, `checked_in` в это
  множество сознательно не включил (перенос события, которое уже отметило
  кого-то на входе, — вырожденный случай вне интересов этого этапа).
- **Проверка перед «отправкой» — универсальная для всех типов**, как и было
  явно указано в задаче (не только для `reminder`): (1) статус регистрации —
  если `cancelled`, `skip_reason='registration_no_longer_active'`; (2)
  `notification.schedule_version = event.schedule_version` (текущая) — иначе
  `skip_reason='stale_schedule_version'`; (3) только для `reminder` —
  `event.starts_at > now()`, иначе `skip_reason='event_already_started'`.
  **Важное наблюдение, обнаруженное при проверке (не гипотеза, а фактически
  воспроизведено):** правило (2), применённое универсально, означает, что
  `ticket`/`waitlist`-уведомление, которое ещё не успели обработать до
  переноса даты, будет помечено `skipped`, а не отправлено — участник в этом
  случае получит `reschedule`-письмо, но не получит исходное подтверждение
  места/очереди. Реализовал именно так, как было явно указано в задаче
  (проверка общая, не только для `reminder`), и фиксирую это как осознанный,
  а не случайно пропущенный эффект — альтернатива (не проверять версию для
  ticket/waitlist) не была запрошена и добавила бы асимметричную логику по
  типам сверх того, что описано.
- **Новые столбцы `processed_at`, `skip_reason`** в `notifications`
  (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, тот же идемпотентный
  `schema.sql`) — видно организатору в «Письмах» как причину, по которой
  письмо не ушло, не только сам факт `skipped`.
- **Логи воркера** — только `notification <id> (<type>) -> sent|skipped:
  <reason>`; ни разу не выводится `payload` целиком (там `access_token`
  внутри `my_registration_url` и `ticket_code`).
- **Точка входа — и фоновый интервал в `index.ts` (30с, `WORKER_INTERVAL_MS`),
  и отдельный CLI `npm run worker`** (`workerCli.ts`) для ручного/тестового
  одноразового тика — без него нельзя было бы детерминированно проверить два
  одновременных воркера или «после переноса, до обработки».
- **Не заявляю exactly-once для настоящего SMTP** — реальной отправки нет;
  гарантия — на запись (уникальный индекс, ровно одна попытка «отправки» на
  запись за счёт `SKIP LOCKED`), а не на фактическую доставку куда-либо.

## 2026-09-30, 13:55–14:01 (Asia/Bishkek) — исправление обработки по типам (нарушение ТЗ)

По итогам ревью нашли реальное нарушение сценария кейса: универсальная
проверка `schedule_version` для всех типов писем (введённая этой же сессией
чуть раньше) означала, что быстрый перенос даты **до** обработки лишал
участника единственного письма с билетом или доступом к очереди — участник
получал только уведомление о переносе. Это подтверждено фактическим
воспроизведением в предыдущей записи, но было ошибочно оставлено как
«осознанный компромисс» вместо того, чтобы признать нарушением требований
кейса («Зарегистрировавшийся получает письмо с билетом», «Кто-то отказался —
первый из листа автоматически получает место и письмо» — эти гарантии не
должны зависеть от того, успел ли воркер сработать до переноса).

Исправлено в `worker.ts`, по типам:

- **`reminder`/`reschedule`** — проверка версии расписания осталась: они
  сообщают конкретную дату, старая версия для них означает, что письмо
  просто устарело (по нему либо уже отправлено, либо будет отправлено свежее
  для актуальной версии).
- **`ticket`/`waitlist`** — проверка версии убрана полностью. При отправке
  `payload.event_title`/`payload.starts_at` перезаписываются актуальными
  значениями из `events` в той же `UPDATE`, что помечает письмо `sent` — участник
  получает корректную дату, даже если она изменилась после постановки письма
  в очередь.
- **Новое правило специально для `waitlist`**: если регистрация уже не
  `waitlisted` (продвинута в `confirmed`/`checked_in`), письмо про очередь
  пропускается (`skip_reason: promoted_since_queued`) — у участника уже есть
  отдельное `ticket`-письмо, созданное в момент продвижения, дублировать
  сообщение о месте незачем.
- **`cancelled` пропускает письмо любого типа** — это правило не менялось,
  просто вынесено отдельной проверкой раньше остальных (приоритет: сначала
  cancelled, потом waitlist-специфика, потом версия для reminder/reschedule).
- **Напоминания теперь получают и `checked_in`-участники**, не только
  `confirmed` — `REMINDER_RECIPIENT_STATUSES = ['confirmed', 'checked_in']` в

## 2026-09-30, 14:05–14:13 (Asia/Bishkek) — блокировка event/registration внутри воркера

Ревью нашло реальную дыру: `SELECT ... FOR UPDATE OF n SKIP LOCKED` блокирует
только `notifications`; `registrations`/`events`, присоединённые обычным
`JOIN`, не лочились вовсе. Решение sent/skipped принималось по снимку,
прочитанному в момент этого join-а, а не по состоянию на момент `COMMIT` —
конкурентная отмена регистрации или перенос события, успевшие закоммититься
между этим чтением и коммитом воркера, никак не блокировались и не были бы
учтены.

Исправление в `processOnePendingNotification` (`worker.ts`): после захвата
`notification` (`FOR UPDATE SKIP LOCKED`, как и раньше) — **два отдельных
`SELECT ... FOR UPDATE`** (обычный, не `SKIP LOCKED`) в той же транзакции:
сначала `events` по `event_id`, затем `registrations` по `registration_id`.
Решение sent/skipped считается только по этим двум результатам, не по
данным из первого запроса.

Порядок блокировок — **event, затем registration** — специально выбран
таким же, как в `cancelMyRegistration` и `updateEvent` (оба лочат event
первым шагом, `cancelMyRegistration` — registration вторым). Одинаковый
порядок во всех трёх местах исключает цикл ожидания: если бы где-то порядок
был обратным, два конкурентных обработчика могли бы взаимно ждать друг
друга (классический deadlock). Здесь же худшее, что может случиться, —
воркер или конкурентный запрос подождёт на `event`-локе до чужого `COMMIT`,
и увидит уже свежие данные.

Проверка сделана на уровне «сырого» SQL (два `psql`-скрипта, повторяющие
точно ту же последовательность блокировок, что и код, с управляемой паузой
`pg_sleep`), а не через искусственную задержку в самом коде — это позволило
детерминированно, а не по случайному таймингу, поставить конкурентный запрос
ровно в нужную точку интерлива:

- **Тест A (воркер держит `event` первым):** воркер лочит `event`, «спит» 4с,
  затем лочит `registration`; параллельно в момент сна отправлен реальный
  `POST /api/my/:token/cancel`. Запрос `cancel` занял ~3.1с — всё это время
  ждал на локе `event`, ни разу не увидел промежуточного состояния. После
  `COMMIT` воркера (`registration.status` было прочитано ещё `'confirmed'`,
  билет помечен `sent`) `cancel` сразу же прошёл и перевёл регистрацию в
  `cancelled`. Итог: `sent` + `cancelled` — валидный порядок «воркер раньше
  отмены», без искажения (билет ушёл, пока место было реально подтверждено).
- **Тест B (обратный порядок):** воркер захватывает `notification`, но перед
  тем как лочить `event`, «спит» 4с; за это время реальный `cancel` проходит
  полностью и мгновенно (0.02с — ничего не держало лок). Когда воркер
  просыпается и лочит `registration`, он читает уже `'cancelled'` — то есть в
  реальном коде это дало бы `skipped: registration_cancelled` по свежим, а
  не устаревшим данным.
- **Тест C (перенос вместо отмены):** воркер держит `event`, параллельно
  отправлен `PATCH /api/events/:id` с новой датой. `PATCH` занял ~3.1с — по
  той же причине, `updateEvent` лочит тот же `event` первым шагом. После
  `COMMIT` воркера (билет отправлен с датой ДО переноса — воркер успел
  раньше) перенос прошёл, `schedule_version` увеличился. Deadlock не
  возник ни разу за все три сценария.
- **Два реальных воркера (`npm run worker`) параллельно** — перепроверено с
  исправленным кодом: 8 pending-записей (включая случайно оставшуюся с теста
  B) разошлись между воркерами без единого пересечения id, 0 дублей по всей
  таблице (`GROUP BY ... HAVING count(*) > 1` — 0 строк), 0 записей осталось
  в `pending`.

## 2026-10-01, 11:50–12:13 (Asia/Bishkek) — найден и исправлен дефект: коллизия ticket_code при продвижении из очереди не обрабатывалась

Отложенный с этапа 3 пробел (см. память агента): `registerWithRetry` уже умел

обработчик `cancelMyRegistration`.

продолжить, только начать заново).

## 2026-10-01, 13:14–13:24 (Asia/Bishkek) — ревью новых сценариев: две реальные проблемы в проверках 7/8

При ревью (до коммита) найдены и исправлены две проблемы в только что
добавленных сценариях:

1. **Обе новые проверки опирались на агрегатные счётчики

   `remindersCreated`/`notificationsProcessed` могли не совпасть с
   ожиданием, даже если уведомления тестового события обработались
   правильно — ложный провал, не связанный с реальным дефектом. Исправлено:

   `event_id`/`registration_id` именно этого прогона, и ни разу не проверяют
   возвращаемое значение тика.

   намеренно создаёт due-напоминание и не обрабатывает его сразу, чтобы оно
   осталось pending к моменту переноса — но если в этот момент успеет
   сработать собственный `runWorkerTick()` backend (каждые

   переноса, и проверка устаревания ничего не докажет. Исправлено: README и
   комментарий в коде теперь явно требуют поднимать backend с большим
   `WORKER_INTERVAL_MS` (например, `3600000`) на время сценария; сам

   себя маленький интервал (сигнал на основе собственного `.env` сценария,
   не живой опрос backend — та же оговорка, что и у требования про общий
   `DATABASE_URL`).
