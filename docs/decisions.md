# Журнал решений

Формат: дата и время в Asia/Bishkek (реальные, по ходу работы), что сделано,
почему так, а не иначе. Запись делается в процессе или сразу после этапа, не
задним числом.

## 2026-09-29, 14:50–15:25 (Asia/Bishkek) — Этап 1: каркас

Начало сессии зафиксировано инструментом (лог сессии Claude Code,
`2026-09-29T08:50:15Z` UTC = `14:50` Asia/Bishkek).

Решения:

- **Backend: Node.js + TypeScript + Express.** Один язык на весь стек, минимум
  зависимостей для API такого размера.
- **PostgreSQL, отдельный контейнер через docker-compose.** Порт хоста — 5433,
  а не стандартный 5432: на машине уже работает Postgres другого проекта
  (`messenger_db`) на 5432, конфликтовать с ним нельзя.
- **Frontend: React + Vite**, сгенерирован официальным шаблоном
  `create-vite react-ts`, стартовая страница заменена на минимальную проверку
  связи с backend (fetch `/health/db`).
- **CORS.** Backend и frontend — разные origin (порты 3000 и 5173), браузер
  блокирует такие запросы без заголовков CORS. Добавлен пакет `cors` с открытой
  политикой для локальной разработки (`origin: *`). Для продакшена это нужно
  сузить, но проект локальный — отмечаю как осознанное упрощение.
- **Время: UTC в базе и в бэкенде, отображение — фиксированный Asia/Bishkek.**
  Без выбора часового пояса пользователем (в отличие от кейса 1 Notetaker, где
  это требование) — для регистрации на мероприятия это не требуется явно,
  упрощение сознательное.

Уточнения архитектуры (приняты до начала кода, будут реализованы на следующих
этапах):

- Уведомления: таблица `notifications` с уникальным ключом
  `(registration_id, type, schedule_version)`, вставка `ON CONFLICT DO NOTHING`
  в той же транзакции, что меняет состояние. Гарантия — «ровно одна запись-
  намерение», не exactly-once доставка через SMTP (доставка эмулируется).
- `schedule_version` на событии, инкремент при переносе даты — открывает новое
  окно для одного нового напоминания на участника без потери истории старых.
- Повторная регистрация после отказа: частичный уникальный индекс
  `(event_id, lower(email)) WHERE status <> 'cancelled'` — отменённая запись
  остаётся как история, новая регистрация создаёт новую строку и заново
  проходит логику лимита/листа ожидания.

Проверка этапа:

- `docker compose up -d db` → контейнер `eventflow-db-1` в состоянии `healthy`.
- `curl http://localhost:3000/health` → `{"status":"ok"}`.
- `curl http://localhost:3000/health/db` → `{"status":"ok","now":"<UTC>"}` —
  подтверждает реальное подключение к PostgreSQL, а не заглушку.
- Открыл `http://localhost:5173` в браузере (Chrome, через инструмент
  автоматизации) — страница показывает статус backend и время БД, то есть
  кросс-origin fetch с 5173 на 3000 реально проходит (CORS настроен верно).
- После проверки оба dev-сервера остановлены (`kill` по портам 3000 и 5173).

Не сделано на этом этапе (осознанно, по плану): схема БД для событий и
регистраций, любая бизнес-логика, UI регистрации/билета — по плану это следующий
этап (30 сентября).

## 2026-09-30, 08:14–08:21 (Asia/Bishkek) — Этап 2: миграции, авторизация, CRUD события

Перед стартом уточнили дизайн (обсуждение, не код): `access_token` (секрет для
своей регистрации) отделён от `ticket_code` (для чекина); уведомление о месте в
листе ожидания — отдельный тип `waitlist` с access_token, билет по продвижению —
отдельным письмом типа `ticket`; повторный `POST` на активный email должен
отвечать нейтрально, без статуса и секретов; занятые места = `confirmed +
checked_in`; `seq` для FIFO присваивается внутри транзакции с блокировкой
события; воркер отправки перепроверяет актуальность перед отправкой (отдельно
от поллера, который только создаёт записи); нельзя уменьшить `capacity` ниже
уже занятых мест.

Решения этапа:

- **Схема без фреймворка миграций.** Один идемпотентный файл
  `backend/db/schema.sql` (`create table if not exists` + `create index if not
  exists`), применяется скриптом `npm run migrate`. На размере проекта
  отдельный migrations-фреймворк (knex/node-pg-migrate) — лишняя зависимость;
  если схема начнёт часто меняться версионно, это станет ограничением —
  фиксирую как известный компромисс.
- **`notifications.type`** уже включает `waitlist` (создаётся при постановке в
  очередь) наравне с `ticket`/`reminder`/`reschedule`, хотя сама рассылка
  появится позже — так схема не потребует правки, когда дойдём до Registration
  API.
- **Auth — одна учётная запись организатора.** Таблица `organizers`, сид из
  `.env` (`ORGANIZER_EMAIL`/`ORGANIZER_PASSWORD`, `bcryptjs`), сессия — JWT в
  httpOnly-cookie (`jsonwebtoken`, `SESSION_SECRET` из `.env`, срок 12ч).
  `requireOrganizer` защищает все `/api/events*`. Без ролей, без восстановления
  пароля — минимум, достаточный для локального теста.
- **CORS сужен.** Было `cors()` с `origin: '*'` (этап 1); теперь куки на
  каждый запрос нужны для авторизации, а `credentials: true` несовместимо с
  `origin: '*'` — заменил на явный `FRONTEND_ORIGIN` (`http://localhost:5173`
  по умолчанию).
- **Правило порядка PATCH:** `schedule_version` растёт только при изменении
  `starts_at`; проверка `capacity < occupied` — только при изменении
  `capacity`; обе проверки и апдейт — в одной транзакции с
  `SELECT ... FOR UPDATE` на строку события.

Проверка этапа (полный список ниже, в ответе пользователю) — миграция и сид на
пересозданной с нуля БД, вход/отказ в доступе без cookie, создание события с
датой в прошлом отклонено, смена только `capacity` не трогает
`schedule_version`, смена `starts_at` увеличивает версию на 1, ограничение
`capacity < occupied` проверено на тестовых данных, вставленных напрямую в
`registrations` (Registration API в этом этапе не существует), два
одновременно открытых окна браузера после независимого логина видят один и тот
же список событий, редактирование в UI корректно показывает время в
Asia/Bishkek.

Не сделано (по плану, следующий этап): регистрация участника, лист ожидания,
чекин, реальная рассылка уведомлений, WebSocket.

## 2026-09-30, 08:37–08:43 (Asia/Bishkek) — точечные исправления этапа 2 перед коммитом

По итогам независимого ревью внесены правки, до коммита:

- **Единая валидация для POST и PATCH.** Вынесена в `backend/src/validation.ts`
  (`parseTitle`/`parseDescription`/`parseStartsAt`/`parseCapacity`,
  `ValidationError`). Раньше `updateEvent` был мягче создания: принимал пустой
  `title`, нестроковый `description` и, главное, **перенос события в прошлое**
  (проверка «дата в будущем» была только в `createEvent`). Теперь оба
  обработчика используют одни и те же функции.
- **Внутренние ошибки БД не возвращаются клиенту.** `handleError` в
  `events.ts`: `ValidationError` → `400` с текстом ошибки (безопасен, это наш
  же текст), любая другая ошибка → `500 {"error":"internal_error"}`, реальная
  причина только в `console.error` на сервере.
- **Найден и исправлен более серьёзный баг при проверке предыдущего пункта:**
  при обрыве соединения с БД процесс backend падал целиком (необработанное
  событие `'error'` на `pg.Pool` — см. https://node-postgres.com/apis/pool#error).
  Без этого воспроизвести «клиент не видит внутренний текст ошибки» было
  невозможно: ошибка не долетала до клиента вообще, потому что процесс был
  уже мёртв. Добавлен `pool.on('error', ...)` в `db.ts`. Это не было
  запрошено отдельно, но напрямую блокировало проверку — исправлено в рамках
  того же точечного изменения.
- **Воспроизводимый SQL-сценарий для capacity** сохранён в
  `backend/db/fixtures/capacity_scenario.sql`. При первой версии сценарий тихо
  вставлял только 1 из 3 строк: `ticket_code` уникален глобально, а литералы
  `'TICKET-A'`/`'TICKET-B'` уже были заняты более ранними ручными тестовыми
  данными в той же локальной БД — `ON CONFLICT DO NOTHING` (без указания цели)
  тихо съел именно эти вставки. Заметил по тому, что проверка
  `capacity=1 → 400` неожиданно прошла как `200`. Исправлено: коды генерируются
  случайно (`'TICKET-' || upper(encode(gen_random_bytes(4), 'hex'))`), email
  сделаны специфичными для фикстуры (`capacity-fixture-*@example.com`), чтобы
  не пересекаться с данными из будущих ручных тестов.
- **Проверил `FRONTEND_ORIGIN` в `index.ts` побайтово** (`od -c`) — обычная
  строка `"http://localhost:5173"`, без markdown-разметки.

Все проверки (auth, валидация POST/PATCH построчно, перенос в прошлое,
`schedule_version`, ограничение `capacity`, устойчивость к падению БД)
повторены с нуля на пересозданной БД — результаты в ответе пользователю.
Не закоммичено.

## 2026-09-30, 08:44–08:49 (Asia/Bishkek) — ужесточение validation.ts перед коммитом

Второй раунд правок по итогам ревью, только `validation.ts`:

- **`parseCapacity`** раньше приводил через `Number(value)`, из-за чего
  строка `"3"`, `null` (→ `0`, отклонялось по `<= 0`, но случайно, не по типу)
  и `boolean` (`true` → `1`, реально прошло бы как `capacity=1`!) вели себя
  непредсказуемо. Теперь строгая проверка `typeof value !== "number"` —
  строки, `null`, `boolean` и дробные отклоняются на уровне типа, а не
  приведения.
- **`parseStartsAt`** раньше принимал любую строку, которую понимает
  `new Date(...)`, включая `"2026-11-01T10:00:00"` без зоны — такая строка
  парсится JS как локальное время процесса, то есть один и тот же запрос
  давал бы разный момент в UTC в зависимости от `TZ` окружения, где запущен
  backend (в контейнере — обычно UTC, на чьей-то машине — нет). Добавлена
  проверка регулярным выражением на обязательный `Z` или `±HH:MM` перед
  парсингом.

Проверено (POST и PATCH, полная матрица) — результаты в ответе пользователю:
`capacity` как строка/`null`/`boolean`/дробное/отрицательное/ноль отклонены,
целое положительное число проходит; `starts_at` без зоны отклонён и на POST,
и на PATCH, `Z` и `+06:00` — приняты и дают одинаковый момент в UTC, мусорная
строка и число вместо строки отклонены.

Закоммичено (см. `git log`), запушено в `origin/main`.
